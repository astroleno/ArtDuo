# DeepSeek V4 Flash 分任务提示词流式 Eval

## 结论

把文本请求拆成独立的 `emotion_response`、`artwork_intro`、`exhibition_preface`、`exhibition_closing` 四路后，DeepSeek V4 Flash 的输入与时延均明显下降，双评估员语义均分没有下降。但简单四路路由会把少数 evidence state 混在一起，不能整包替换现有 v3；需要在任务路由下再增加“明确情绪白名单、确定作品描述、不确定归属、档案记录残片”等证据 profile。

本轮共完成 **228 次** DeepSeek 流式请求：全部 HTTP 200、全部收到首个文本 chunk、全部可解析为约定 JSON、thinking 字符均为 0。

## 生产代码现状

- 策展分析/意图：已有独立结构化提示词，位于 `real-llm-curation-intent-fixed.ts`。
- 作品介绍/讲解：已有独立提示词，位于 `artwork-explanation.ts`。
- 前言与结语：当前 `route.ts` 的 `generateNarration()` 仍在一次调用中同时生成；服务端等待两段都完成后才发送前言事件。
- `generateCurationSummary()` 是另一个独立总结提示词，但当前未找到调用方。
- 当前路由把 `emotion` 和 `userInput` 两个参数传给只接收一个参数的 `generateCurationIntent()`；第二个参数会被忽略。这是接入提示词前必须核对的输入丢失风险。

因此答案不是“现在全部都分开了”：策展意图与作品讲解已经分开，前言与结语仍合并。本轮只在 eval harness 中验证拆分方案，尚未改生产链路。

## v3 与 task-routed-v4：同批 120 次 A/B

| 指标 | source-isolated-v3 | task-routed-v4 | 变化 |
|---|---:|---:|---:|
| 样本 | 60 | 60 | — |
| 平均输入 tokens | 444.5 | 317.5 | **-28.6%** |
| TTFT 中位数 | 618.5 ms | 505 ms | **-18.4%** |
| 总时间中位数 | 1487 ms | 1325.5 ms | **-10.9%** |
| 平均输出 tokens | 95.73 | 91.97 | -3.9% |
| JSON 可用率 | 100% | 100% | 持平 |
| deterministic hard pass | 46.7% | 43.3% | -3.4pp |

hard pass 的差异主要来自中文字数下限，不等于语义越界。v4 的 framing 输入从平均 693.5 降到 369 tokens，TTFT 从 707.5ms 降到 525.5ms，总时间从 1505.5ms 降到 1324.5ms。

总体质量持平略升，但变化集中在 case family：

- v4 明显改善：中性情绪、隐私边界、记录冲突、不确定归属、修补前言、夜景结语、纪念物结语。
- v4 明显回退：道歉后更生气、北斋诗画反差、残缺档案前言。
- 两位评估员都不建议把 v4 整包全量替换 v3。

## v4.1：强制字数方案被拒绝

v4.1 在四路提示词中加入目标字数与句数。60 次流式请求显示：输入上升至 339.7 tokens，TTFT 回到 606ms，总时间回到 1440.5ms；整体 hard pass 降到 40%，framing hard pass 只有 5%。DeepSeek 并未因“更高目标字数”稳定达到中文字符下限，反而更慢、更短，因此不采用 v4.1。

这说明当前字数问题不应继续通过堆提示词解决。更合理的选择是调整产品允许的自然长度，或使用确定性的后置长度策略，但不能用自由扩写来补字数。

## v4.2：证据 profile 定向修复

v4.2 针对三类回退增加状态约束：

- 道歉情绪：只允许“道歉发生、道歉后更生气、原因未知”，不扩写其他情绪或经历。
- 确定作品描述：固定北斋、约 1835 年作品年代、题诗与画面已描述，防止误套不确定归属模板。
- 档案残片：固定实体单位为“馆藏记录/条”，作品是否存世或可见保持未知。

在三类风险 case 上又完成 48 次同批流式 A/B：

|---|---:|---:|---:|
| 样本 | 24 | 24 | — |
| 平均输入 tokens | 315.33 | 369.33 | +17.1% |
| TTFT 中位数 | 612.5 ms | 583 ms | -4.8%* |
| 总时间中位数 | 1461.5 ms | 1324 ms | -9.4%* |

## 建议架构

最终应使用一个轻量 router，每个请求只选择一个输出任务：

1. `curation_analysis`：结构化策展意图，不承担可读文案。
2. `artwork_intro`：单件作品介绍/讲解。
3. `exhibition_preface`：建立观看入口。
4. `exhibition_closing`：收束已知与未知。
5. `emotion_response`：承接用户情绪与边界。

任务路由下再选择 evidence profile，而不是给所有任务发送一份大提示词。需要同时生成前言和结语时，可共享同一个只读 `curation_packet`，并行发起两个请求；这会减少等待链，但会重复少量公共输入，必须在生产链路中另做端到端验证。

当前最稳妥的 eval 选择是混合路由：v4 用于已经稳定改善的任务族；道歉情绪可用 v4.2；混合情绪、丰富作品描述、稀疏作品与档案残片暂保留 v3，其中丰富作品描述继续做窄补丁与未见 case 验证。

## 判定

- “分开会不会更快”：在本轮单任务同批对照中，**会**，TTFT -18.4%，总时间 -10.9%，输入 -28.6%。
- “语义质量是否保持”：总体保持，双评估员平均 +0.15/20，但不能只看总分。
- “现在是否能上线整包 v4”：**不能**。可以进入按任务族灰度；v4.2 还需要未见 case，尤其是丰富作品描述。
