# 提升文档

## 现状诊断
- 综合测试报告显示粗筛阶段能拉取到大量作品，但在粗筛与评分之间数据即被清空，所有用例的评分统计都为 0（见 `comprehensive-test-report.md:40-68,82-120,200-238`）。
- 同一份报告里情绪曲线点数却保持在 40-60 左右，说明 `ArtworkServiceManager` 的并发抓取阶段已经返回了几十件作品，而问题发生在评分→精选链路。
- `serviceInfo` 段落始终标记“当前服务: Met Museum API”，即便该服务在可用性检查中失败（`comprehensive-test-report.md:102-105`），意味着 `ArtworkServiceManager` 在 `successfulServices` 为空时仍保留默认下标 0，导致监控信息失真。

## 可能原因拆解
1. **批量评分结果没有落地**：`batchJudgeArtworksUltraOptimized` 会在预筛选完成后返回 `totalProcessed`（`frontend/src/lib/curation/llm-judge-ultra-optimized.ts:47-112`）。当前统计恒为 0，推测两种情况：
   - 预筛选返回空数组（需要确认 `smartPreFilter` 的输入/输出日志）。
   - `fallbackBatchScoring` 在 GLM 不可用时返回了空列表，需要检查 `scoreBatchArtworksOptimized` 在捕获网络异常后是否真正回填默认评分。
2. **外部服务成功标记与结果为空**：Met/Rijks API 均在成功路径返回 `success: true`，即便最终 `artworks.length === 0`（例如 `frontend/src/lib/artwork-services/metmuseum-api.ts:70-88`）。当 detail 拉取全部失败时会触发这种情况，从而阻止 `curate` 路由走到本地降级数据。
3. **服务状态汇报缺乏兜底**：`ArtworkServiceManager` 写入 `currentServiceIndex` 时未判断 `successfulServices` 为空（`frontend/src/lib/artwork-services/artwork-service-manager.ts:116-133`），在失败时索引保持 0，造成“当前服务”与真实数据源不符，也让排障困难。
4. **重复/未使用的 LLM 调用**：`generateCurationSummary` 已返回完整策展文本，后续又在路由内额外起一次 `curationDescription` LLM 调用，但最终响应仍使用 summary（`frontend/src/app/api/curate/route.ts:101-170`）。这会消耗额外配额，也让日志混淆。

## 流程中 LLM 与硬编码的分布
- **搜索计划**：首选 GLM 关键词生成，失败时 fallback 到 OpenAI；若 LLM 不可用则使用 `PRECISE_EMOTION_KEYWORDS`（`frontend/src/lib/curation/search-plan-ultra-optimized.ts:84-130`）。
- **数据抓取（Met/Rijks/MCP）**：完全依赖官方 API，无 LLM；缺省 fallback 服务使用硬编码样例（`frontend/src/lib/artwork-services/fallback-service.ts:9-117`）。
- **批量评分**：主路径调用 GLM 批处理；当不可用时退回到 `fallbackBatchScoring` + 默认评分（`frontend/src/lib/curation/llm-judge-ultra-optimized.ts:47-249`）。
- **情绪曲线生成**：纯算法/硬编码模板（`frontend/src/lib/curation/emotion-curve.ts:32-205`）。
- **智能精选**：纯算法（`frontend/src/lib/curation/artwork-selector.ts:1-200`）。
- **作品讲解与策展总结**：优先 GLM，失败时降级到 OpenAI，再失败使用模板（`frontend/src/lib/curation/artwork-explanation.ts:1-215,231-283`）。
- **最终 `curationDescription`**：再次调用 GLM/OpenAI（`frontend/src/app/api/curate/route.ts:136-170`），但结果未写入响应。

## 提升建议
- **修正评分阶段的退化行为**：在 `batchJudgeArtworksUltraOptimized` 内新增日志校验 `preFilteredArtworks.length`、`finalScores.length`，并在两者为 0 时主动抛错，触发外层 fallback 或默认评分，避免静默返回 0。
- **统一服务成功准则**：在 Met/Rijks 服务中，当 `artworks.length === 0` 时强制返回 `success: false`，让管理器走降级流；同时对 `successfulServices` 为空的情况补上兜底索引与状态上报，保证 `serviceInfo` 可信。
- **明确离线策略**：提供一个显式的“无网络评分”配置，直接回退到权重计算/规则表，而不是多层 LLM 尝试，缩短 0→fallback 的耗时。
- **清理冗余 LLM 调用**：复用 `generateCurationSummary` 的结果作为最终描述或将两次调用合并，减少一次外部请求。
- **加固监控**：在响应 diagnostics 中增加“粗筛数量”、“预筛数量”、“最终评分数量”三项统计，可快速定位断点位置。

## 调试验证建议
1. 在评分模块加入临时日志（或使用现有 `test/debug-coarse-selection.js`）核对 `预筛 → 评分 → 默认评分` 每一步的长度差异。
2. 修改服务返回条件后，再跑一次 `comprehensive-test.js` 和 `test/debug-coarse-selection.js`，确认 `totalProcessed` 不再是 0。
3. 若需验证离线 fallback，可暂时屏蔽外网请求，确保本地数据链路能返回 ≥9 件作品。
4. 观察 `serviceInfo` 是否准确地报告为 `fallback` 或真实服务名，确认新增兜底生效。
