# 提示词提升

## LLM 使用位置总览
- 搜索计划关键词生成：`frontend/src/lib/curation/search-plan-ultra-optimized.ts:84-130`、`frontend/src/lib/glm-optimized-client.ts:310-365`
- 服务端批量/单个评分：`frontend/src/lib/curation/llm-judge-ultra-optimized.ts:140-352`、`frontend/src/lib/curation/llm-judge.ts:38-137`
- 作品讲解与策展总结：`frontend/src/lib/curation/artwork-explanation.ts:65-214`、`frontend/src/lib/curation/artwork-explanation.ts:231-283`
- 最终策展说明（服务端响应）：`frontend/src/app/api/curate/route.ts:136-170`
- 前端 Agent：情绪分析、评分、策展说明分别位于 `frontend/src/lib/frontend-agent.ts:181-209`, `frontend/src/lib/frontend-agent.ts:392-441`, `frontend/src/lib/frontend-agent.ts:450-508`

以下针对每处提示词提出优化建议，并给出可直接替换的优化版本（保留现有语义，重点强化格式约束与信息覆盖）。

## 搜索计划关键词生成
- **现状**：提示词要求“生成5个关键词，用逗号分隔”，但返回自由文本，经常混入说明性语句；没有限定必须英文；缺少结构化输出，后续解析需 split。
- **改进方向**：
  1. 直接要求输出 JSON，并声明字段含义与语言要求。
  2. 补充“如果无法找到足量关键词，保留已知并用 `"fallback": true` 标记”之类兜底，方便判断。
  3. 明确禁止额外文字，避免 ```json 包裹。
- **优化示例**（`frontend/src/lib/glm-optimized-client.ts:326` 及 `frontend/src/lib/curation/search-plan-ultra-optimized.ts:150` 可复用）：
  ```text
  你是一位专业的艺术策展人，负责为情绪主题生成检索关键词。
  任务：为情绪 "{{emotion}}"（用户补充："{{userInput}}"）输出 5 个英文检索关键词，覆盖情绪、风格、场景或艺术家维度。
  约束：
  - 输出纯 JSON，不要出现额外文字或 Markdown。
  - 字段 `keywords` 是按优先级排序的字符串数组，必须是小写英文单词或短语。
  - 如果生成数量不足 5 个，请仍使用数组形式并附加布尔字段 `fallback` 为 true。
  - 不得返回与输入情绪完全相同的中文词。
  返回示例：
  {"keywords": ["celebration", "festival", "bright palette", "rococo", "dance"], "fallback": false}
  ```

## 批量评分（GLM 批处理 + 回退批次）
- **现状**：要求“只返回JSON”，但未明确顶层结构；没有绑定 artwork id；理由字段不限定语言；未约束分数范围/精度，导致解析容错逻辑复杂。
- **改进方向**：
  1. 统一输出 schema：`{ "scores": [{ "artwork_id": "...", "emotion_fit": number, ... }] }`。
  2. 明确分值范围与小数位，并要求与输入顺序一致。
  3. 添加 `errors` 数组用于无法评分的作品，方便回退。
- **优化示例**（适用于 `batchScoreWithGLM` 和 `scoreBatchArtworksOptimized`）：
  ```text
  你是一位专业的艺术策展人，请依据情绪 "{{emotion}}" 对下列作品进行评分。保持输入顺序。
  输出要求：
  {
    "scores": [
      {
        "artwork_id": "原始ID",
        "emotion_fit": 0-10 之间的一位小数,
        "artistic_value": 0-10 之间的一位小数,
        "visual_impact": 0-10 之间的一位小数,
        "overall_recommendation": 0-10 之间的一位小数,
        "confidence": 0-1 之间的两位小数,
        "reasoning": "中文或英文，不超过80字"
      }
    ],
    "errors": ["无法评分的 artwork_id"]
  }
  严禁输出除 JSON 以外的内容，也不要使用代码块标记。
  ```

- **单件评分回退**（`frontend/src/lib/curation/llm-judge.ts:57-106`）：同样加上分数范围、语言约束，并提示若缺乏信息可返回默认值同时写入 `notes` 字段。

## 作品讲解 `generateSingleArtworkExplanation`
- **现状**：提示词要求返回 JSON，但未限制字段长度或语言，导致偶发超长段落；`confidence` 缺少格式约束；没有说明要避免 Markdown。
- **改进方向**：
  1. 设置每段建议 80-120 字，并指明语言（目前产品为中文输出）。
  2. 要求 `confidence` 取 0-1 之间两位小数。
  3. 明确禁止额外文本。
- **优化示例**：
  ```text
  请用中文为作品《{{title}}》生成讲解，覆盖情绪关联、艺术分析、历史背景、策展理由、用户相关性五个点。
  输出纯 JSON：
  {
    "emotionalConnection": "80-120字，解释其与情绪'{{emotion}}'的契合",
    "artisticAnalysis": "80-120字，突出技法/风格",
    "historicalContext": "80-120字，概述历史语境",
    "curationReason": "60-100字，说明入选原因",
    "userRelevance": "60-100字，结合用户输入 {{userInput}}",
    "confidence": 0-1 之间的两位小数
  }
  只允许 JSON 本身；若信息缺失，请用 "暂无数据" 占位，并保持字段齐全。
  ```

## 策展总结 `generateCurationSummary`
- **现状**：要求 200-300 字但未限制段落结构；GLM 容易返回 Markdown 标题；缺少对摘要层次的指引。
- **改进方向**：
  1. 规定分段结构，例如三段分别对应主题、作品选择、用户契合。
  2. 明确输出为纯文本且不含标题。
  3. 若作品数为 0，要返回引导用户补充信息的文案。
- **优化示例**：
  ```text
  请用中文撰写 220-260 字的策展总结，分三段输出（用换行分隔）。
  - 第1段：概括情绪主题 "{{emotion}}" 的核心理念。
  - 第2段：说明所选作品（最多提及3件）如何体现此主题。
  - 第3段：强调与用户输入 {{userInput}} 的关联和观展体验。
  禁止使用标题、项目符号、Markdown。
  若作品数量为0，请直接给出温和的引导语，建议用户补充描述。
  ```

## 最终策展说明（路由内二次调用）
- **现状**：与策展总结内容重复，但输出被忽略；若保留，需要提示更简短且用于展示。
- **改进方向**：
  - 若计划继续使用，将提示词缩减为 80-120 字的“陈列语”，并强调不可出现与 summary 相同段落。
  - 明确若输入作品少于 3 件时提供安抚式文案。
- **优化示例**：
  ```text
  根据下列数据，为观众撰写 100 字以内的展览介绍，语气温暖凝练，不得重复输入中的原句：
  {{结构化诊断数据}}
  输出纯文本，无标题、无列表。
  ```

## 前端 Agent 提示词对齐
- **情绪分析 (`frontend/src/lib/frontend-agent.ts:181-209`)**：与后端搜索计划共用 schema，建议同步使用“输出 JSON”规范，增加失败时的 fallback 字段以便前端判断。
- **单件评分 (`frontend/src/lib/frontend-agent.ts:392-441`)**：目前只返回 overall_score，可与后端统一，或者至少返回 `scores` 对象包含 `emotion_fit` 等，减少多端差异。
- **策展说明 (`frontend/src/lib/frontend-agent.ts:450-508`)**：可沿用策展总结的三段式模板，避免出现 Markdown 标题 `#`。

## 统筹建议
1. **统一 schema**：服务端与前端共享同一提示模板 + 解析逻辑，方便缓存与容错。
2. **加入语言提示**：明确输出使用中文或英文，避免双语混杂。
3. **禁止 Markdown**：所有提示都应写明“不要使用代码块/标题”，减轻清洗逻辑。
4. **失败兜底**：鼓励在提示词里设定“若信息不足请给出 reason 并填入 errors”以便程序层识别。

按上述模板逐步替换后，可显著降低 LLM 输出不可解析的概率，也便于日志诊断评分/讲解失败的原因。
