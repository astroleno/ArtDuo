# MCP整合TODO - 智能策展系统重构

## 项目概述

基于`mcp检索.md`和`mcp超量.md`两个框架，重构现有的MCP集成和LLM策展系统，实现真正的"情绪→LLM智能策展→MCP数据获取→LLM智能判定→高质量作品输出"的完整流程。

## 核心目标

1. **真正的AI策展**：LLM参与全流程，不仅仅是关键词生成
2. **智能置信度**：LLM对每个作品进行智能评分和理由说明
3. **性能优化**：解决MCP搜索结果过多导致的性能问题
4. **一次调用完成**：前端只需要一次请求，后端内部完成所有步骤
5. **渐进式加载**：首屏快速响应，详情分批水合

## 技术架构

### 4阶段流程设计
```
Phase 1: 计划生成 → Phase 2: 数据获取 → Phase 3: LLM判定 → Phase 4: 汇总输出
```

### 分层处理策略
```
召回（轻）→ 分面精炼 → 重排多样化 → 详情水合
```

## 详细任务清单

### 1. 架构分析与设计
- [ ] **分析当前架构** - 评估现有MCP集成和LLM策展流程的优缺点
- [ ] **设计统一框架** - 结合mcp检索.md和mcp超量.md，设计完整的智能策展系统架构

### 2. Phase 1 - 计划生成
- [ ] **实现Phase 1 - 计划生成**：LLM生成检索计划（JSON格式），包含查询策略和过滤条件
  - 情绪分析 → 关键词生成
  - 搜索策略制定
  - 过滤条件设置
  - 目标数量规划

### 3. Phase 2 - 数据获取
- [ ] **实现Phase 2 - 数据获取**：优化MCP搜索，实现分层召回（轻量级搜索+智能精炼）
  - 轻量级搜索：只返回objectIDs，不做详情水合
  - 智能精炼：当结果过多时，LLM提出精炼策略
  - 批量处理：优化MCP调用，支持批量获取
  - 并发控制：限制并发数，避免超时

### 4. Phase 3 - LLM智能判定
- [ ] **实现Phase 3 - LLM智能判定**：让LLM对每个作品进行评分和理由说明，输出结构化结果
  - 作品评分：0-1分的情绪匹配度
  - 理由说明：为什么选择/拒绝这个作品
  - 结构化输出：JSON格式的判定结果
  - 迭代优化：支持补检和重新判定

### 5. Phase 4 - 汇总输出
- [ ] **实现Phase 4 - 汇总输出**：按LLM评分排序，实现多样化处理和去重机制
  - 评分排序：按LLM评分降序排列
  - 多样化处理：避免重复和相似作品
  - 去重机制：同一作者/同题材相似度>0.6只留一件
  - 最终输出：高质量的作品列表

### 6. 性能优化
- [ ] **实现渐进式加载** - 首屏快速响应，详情分批水合，支持流式输出
  - 首屏响应：≤1s返回作品ID列表
  - 详情水合：分批并发获取详情
  - 流式输出：支持SSE流式返回
  - 加载更多：支持分页和懒加载

- [ ] **实现性能优化** - 并发控制、超时管理、缓存机制、延迟预算控制
  - 并发控制：详情水合并发6-10，单条超时3-5s
  - 延迟预算：单轮≤2s，p95总完成≤4-6s
  - 缓存机制：结果缓存，避免重复调用
  - 超时管理：指数退避，最多3次重试

### 7. 错误处理与监控
- [ ] **实现错误处理** - 各阶段失败处理、降级策略、重试机制
  - 阶段失败：各阶段的错误处理和恢复
  - 降级策略：MCP→API→本地数据的降级
  - 重试机制：网络错误的重试和退避
  - 超时处理：请求超时的优雅处理

- [ ] **实现监控日志** - 性能指标、调用统计、错误追踪、调试信息
  - 性能指标：响应时间、成功率、并发数
  - 调用统计：MCP调用次数、LLM调用次数
  - 错误追踪：错误类型、错误频率、错误堆栈
  - 调试信息：详细的执行日志和状态信息

### 8. 测试与优化
- [ ] **测试完整系统** - 端到端测试，性能测试，用户体验测试
  - 端到端测试：完整的策展流程测试
  - 性能测试：延迟、并发、稳定性测试
  - 用户体验测试：响应时间、错误处理、加载状态
  - 压力测试：高并发、大数据量测试

- [ ] **优化用户体验** - 流式输出、进度显示、错误提示、加载状态
  - 流式输出：实时显示搜索进度
  - 进度显示：各阶段的完成状态
  - 错误提示：友好的错误信息和恢复建议
  - 加载状态：清晰的加载指示器

## 技术参数

### 性能参数
- **首屏响应**：≤1s返回作品ID列表
- **精炼触发**：total>80触发精炼，total>300强制切分
- **并发控制**：详情水合并发6-10，单条超时3-5s
- **延迟预算**：单轮≤2s，p95总完成≤4-6s

### 判定参数
- **候选字段**：≤6项（id/title/artist/date/tags/thumb）
- **输出格式**：`{accepted[], rejected[], need_more, next_plan}`
- **多样化阈值**：同一作者/同题材相似度>0.6只留一件
- **置信度阈值**：≥0.3的作品才被接受

## 技术栈

### 前端
- **Next.js 15.5.3** - 全栈React框架
- **React 19.1.0** - 前端UI库
- **Tailwind CSS v4** - 样式框架
- **Framer Motion** - 动画库
- **SSE流式输出** - 实时数据推送

### 后端
- **Next.js API Routes** - 后端API（不是独立Node.js服务器）
- **BigModel GLM-4.5** - LLM服务
- **metmuseum-mcp** - MCP服务
- **Python MCP客户端** - 通过child_process调用

### Agent框架选择
- **当前**：简单的服务管理器模式
- **可选升级**：
  - **LangGraph** - 多阶段代理，强控制/可观察，适合复杂工作流
  - **OpenAI Responses API** - 模型原生MCP支持，一次调用完成
  - **Claude工具调用** - 模型主导，多轮工具调用
  - **LlamaIndex** - 检索与重排组件现成，适合检索优化

### 框架决策建议
**推荐方案**：
1. **短期**：继续使用当前的服务管理器模式，优化现有实现
2. **中期**：考虑升级到LangGraph，实现真正的多阶段代理
3. **长期**：如果性能要求极高，考虑OpenAI Responses API的原生MCP支持

**选择标准**：
- **控制力**：需要细粒度控制 → LangGraph
- **简单性**：希望模型自主完成 → OpenAI/Claude原生支持
- **性能**：检索和重排优化 → LlamaIndex

### 数据存储
- **本地缓存** - 结果缓存，避免重复调用
- **内存存储** - 临时数据存储

## 部署策略

### 方案0：纯前端MVP（最推荐）
**适用场景**：快速MVP，零服务器成本
- **架构**：前端直接调用LLM + MCP服务
- **部署**：Vercel静态托管（免费）
- **Agent**：React状态机 + Web Workers
- **优势**：
  - 零服务器成本
  - 部署简单（git push）
  - 响应速度快
  - 支持离线使用
  - 移动端完美支持
- **实现**：
  - 前端直接调用BigModel GLM API
  - 前端直接调用MCP服务
  - 本地Agent逻辑（状态机）
  - 智能缓存（IndexedDB）

### 方案1：纯Vercel部署（推荐）
**适用场景**：快速上线，成本控制
- **前端**：Vercel (Next.js)
- **后端**：Vercel API Routes
- **限制**：60秒超时，需要优化性能
- **优化策略**：
  - 简化MCP调用流程
  - 实现渐进式加载
  - 使用缓存减少重复调用
  - 避免使用LangGraph

### 方案2：混合部署（最佳性能）
**适用场景**：生产环境，高性能要求
- **前端**：Vercel (Next.js)
- **后端**：Railway/Render/AWS (LangGraph + MCP)
- **优势**：无时间限制，可以使用完整框架
- **成本**：更高，需要管理两个服务

### 方案3：渐进式升级
**实施步骤**：
1. **第一阶段**：纯Vercel部署，优化现有实现
2. **第二阶段**：根据性能需求，考虑混合部署
3. **第三阶段**：引入LangGraph等高级框架

### 移动端支持
- **响应式设计**：Tailwind CSS确保移动端适配
- **PWA支持**：可安装到手机桌面
- **性能优化**：SSR/SSG提升加载速度
- **离线支持**：Service Worker缓存

3. **性能优先**：重点关注延迟控制和并发管理
4. **错误处理**：完善的错误处理和降级机制
